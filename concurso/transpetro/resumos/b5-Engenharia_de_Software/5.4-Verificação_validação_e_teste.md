## Verificação × Validação ⭐⭐

| Aspecto | **Verificação** | **Validação** |
| --- | --- | --- |
| Pergunta | Estamos construindo o software **do jeito certo**? | Estamos construindo o **software certo**? |
| Compara com | A **especificação** | A **necessidade real** do usuário |
| Foco | Conformidade interna | Adequação ao uso |
| Ator típico | Equipe técnica | Usuário / cliente |
| Técnicas | Revisão, inspeção, walkthrough + teste de unidade e integração | Teste de sistema e de **aceitação**, protótipo |

> [!danger] Par invertido — verificação × validação
> Mnemônico: **verificação = conforme a espec**. **validação = o usuário validou.**
> Direção inversa: *"o produto atende ao que o cliente realmente precisa" → qual?*

> [!warning] Verificação NÃO é sinônimo de estático
> Revisão e inspeção são verificação **estática**; teste de unidade e de
> integração são verificação **dinâmica**. O corte verificação/validação é
> pelo **critério de comparação**, não pela execução.

---
## Teste estático × dinâmico ⭐

| | **Estático** | **Dinâmico** |
| --- | --- | --- |
| Executa o código? | **Não** | **Sim** |
| Examina | Documento, modelo, código-fonte | Comportamento em execução |
| Técnicas | Revisão, **inspeção**, walkthrough, análise estática automatizada | Todos os testes que rodam o software |

**Inspeção (Fagan):** revisão **formal**, com papéis definidos (moderador, autor,
revisor), checklist e registro de defeitos. É a mais rigorosa.
**Walkthrough:** informal, conduzido pelo próprio autor.

## Erro × Defeito × Falha ⭐⭐

| Termo | O que é | Onde está |
| --- | --- | --- |
| **Erro (engano/mistake)** | Ação humana equivocada | Na **pessoa** |
| **Defeito (bug/fault)** | O problema introduzido no artefato | No **código/documento** |
| **Falha (failure)** | O comportamento incorreto observado | Na **execução** |

> [!danger] Par invertido — a cadeia
> **Pessoa erra → gera defeito no código → que, ao executar, causa falha.**
> Defeito que nunca é executado **não vira falha**.

## Níveis de teste ⭐⭐

| Nível | Testa | Quem faz |
| --- | --- | --- |
| **Unidade** | A menor parte isolada (método, classe, módulo) | Desenvolvedor |
| **Integração** | A **comunicação entre** os módulos | Desenvolvedor / equipe de teste |
| **Sistema** | O sistema **completo**, contra os requisitos | Equipe de teste |
| **Aceitação** | Se atende à **necessidade do cliente**; libera o uso | **Usuário / cliente** |

> [!warning] O nível mais cobrado é integração
> Unidade testa a peça. **Integração testa a interface entre as peças** — é o
> único que existe para pegar erro de comunicação.

**Estratégias de integração:**

| Estratégia | Como |
| --- | --- |
| **Big bang** | Junta tudo de uma vez e testa. Difícil isolar o defeito |
| **Incremental top-down** | Do módulo de cima para baixo. Usa **stubs** (simulam os módulos chamados) |
| **Incremental bottom-up** | De baixo para cima. Usa **drivers** (simulam quem chama) |

> [!danger] Par invertido — stub × driver
> **Stub substitui quem é chamado** (usado no top-down).
> **Driver substitui quem chama** (usado no bottom-up).
> Mnemônico: **d**river **d**irige de baixo (bottom-up).

**Tipos de teste de aceitação:**
**Alfa** — no ambiente do **desenvolvedor**, com o desenvolvedor presente.
**Beta** — no ambiente do **cliente**, sem o desenvolvedor.

## Caixa-branca × Caixa-preta ⭐⭐

| | **Caixa-branca (estrutural)** | **Caixa-preta (funcional)** |
| --- | --- | --- |
| Conhece o código? | **Sim** — testa a estrutura interna | **Não** — testa entrada → saída |
| Baseia-se em | Caminhos, condições, laços, fluxo de controle | Especificação / requisito |
| Técnicas | Cobertura de comandos, de decisão, de condição; **complexidade ciclomática** | **Particionamento de equivalência**, **análise de valor-limite**, tabela de decisão |
| Nível típico | Unidade | Sistema, aceitação |

> [!danger] Par invertido — branca × preta
> **Branca = vê dentro (estrutura). Preta = não vê (só entrada e saída).**
> Direção inversa: *"testa sem conhecer o código-fonte, só a especificação" → qual?*

**Caixa-cinza:** conhecimento **parcial** da estrutura interna.

### As duas técnicas de caixa-preta que mais caem

**Particionamento de equivalência** — divide as entradas em classes que devem se
comportar igual; testa **um representante** de cada classe.
**Análise de valor-limite** — testa as **bordas** das classes. Campo aceita 1 a 100:
testa 0, 1, 100, 101. É onde o defeito costuma estar.

## Teste de regressão ⭐

Reexecutar testes já existentes para garantir que uma **alteração não quebrou o
que funcionava**. É o principal candidato à **automação**, porque se repete a cada
mudança.

---
## Tipos por objetivo (não funcionais) ⭐

| Tipo | Verifica |
| --- | --- |
| **Desempenho** | Tempo de resposta e throughput sob carga esperada |
| **Carga** | Comportamento com o volume previsto de usuários |
| **Estresse** | Comportamento **acima** do limite, até quebrar |
| **Volume** | Grande quantidade de **dados** |
| **Usabilidade** | Facilidade de uso |
| **Segurança** | Resistência a acesso indevido e ataque |
| **Portabilidade** | Funcionamento em ambientes diferentes |
| **Fumaça (smoke)** | Verificação rápida e superficial se a build **está estável** para ser testada |

> [!danger] Par invertido — carga × estresse
> **Carga = dentro do esperado. Estresse = além do limite, para ver onde quebra.**

## Os 7 princípios de teste ⭐⭐

1. O teste demonstra a **presença** de defeitos, **nunca a ausência**
2. **Teste exaustivo é impossível**
3. **Teste antecipado** compensa (quanto antes, mais barato corrigir)
4. **Agrupamento de defeitos** — poucos módulos concentram a maioria dos defeitos
   (princípio de Pareto)
5. **Paradoxo do pesticida** — repetir os mesmos testes deixa de achar defeitos
   novos; é preciso revisar os casos
6. Teste **depende do contexto** — não se testa e-commerce como software crítico
7. **Ausência de erros é uma ilusão** — software sem defeito mas que não atende à
   necessidade do usuário é inútil

> [!warning] Os dois mais cobrados
> Princípio **1** ("teste não prova ausência de defeito") e princípio **3**
> (custo de correção cresce exponencialmente ao longo do ciclo).

## 9. TDD e automação

**TDD (Test-Driven Development):** escreve-se o **teste antes** do código.
Ciclo **red → green → refactor**: teste falha, implementa o mínimo para passar,
refatora.

**Integração contínua (CI):** cada commit dispara build e bateria de testes
automatizados, detectando a quebra cedo.
