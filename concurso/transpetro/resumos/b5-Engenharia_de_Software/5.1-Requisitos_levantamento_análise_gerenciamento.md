# Requisitos: levantamento, análise e gerenciamento [T-5.1]

## 1. O que é requisito

Condição ou capacidade que o software **deve** ter para atender à necessidade
de um usuário ou resolver um problema. Descreve **o quê**, não **como**.

---

## 2. Classificação ⭐⭐ (o mais cobrado)

### 2.1 Funcional × não funcional

| | **Funcional (RF)** | **Não funcional (RNF)** |
| --- | --- | --- |
| Descreve | O que o sistema **faz** — função, serviço, comportamento | **Como** o sistema faz — restrição, qualidade, atributo |
| Verbo típico | "o sistema deve **permitir/calcular/emitir/cadastrar**" | "deve responder em até 2s", "deve estar disponível 99,9%" |
| Exemplos | Emitir relatório, autenticar usuário, registrar pedido | Desempenho, segurança, usabilidade, disponibilidade, portabilidade, manutenibilidade, escalabilidade |

> [!danger] Par invertido — RF × RNF
> **Funcional = função. Não funcional = qualidade/restrição.**
> Se descreve uma **ação que o sistema executa** → funcional.
> Se descreve **um limite, um atributo ou uma qualidade** → não funcional.
>
> ⚠ Pegadinha clássica: **"o sistema deve criptografar a senha"** parece função,
> mas segurança é **não funcional**. O corte é: a criptografia é *qualidade* do
> tratamento, não um serviço que o usuário pede.
>
> Direção inversa para treinar: *"tempo de resposta máximo de 3 segundos" → qual?*

### 2.2 Requisito de usuário × de sistema

| | Usuário | Sistema |
| --- | --- | --- |
| Linguagem | Natural, alto nível, para o cliente | Detalhada, técnica, para o desenvolvedor |
| Quem lê | Gestor, cliente, usuário final | Analista, arquiteto, desenvolvedor |

### 2.3 Requisito de domínio

Vem da **área de negócio**, não do usuário. Impõe regra própria do setor
(ex.: regra contábil, norma regulatória).

---

## 3. As atividades do processo de Engenharia de Requisitos ⭐

| # | Atividade | O que faz |
| --- | --- | --- |
| 1 | **Elicitação / levantamento** | Descobrir requisitos com os stakeholders |
| 2 | **Análise e negociação** | Classificar, detectar conflito, ambiguidade e omissão; priorizar; negociar |
| 3 | **Especificação / documentação** | Registrar formalmente no **documento de requisitos (ERS)** |
| 4 | **Validação** | Confirmar com o stakeholder que os requisitos estão **certos** |
| + | **Gerenciamento** | Atividade **contínua**, paralela a todas: controla **mudanças** e **rastreabilidade** |

> [!warning] Gerenciamento não é etapa da fila
> Ele **atravessa** todo o processo e continua depois, até o fim do projeto.
> Não é a última etapa.

---

## 4. Elicitação — técnicas ⭐

| Técnica | Quando serve |
| --- | --- |
| **Entrevista** | A mais usada. Estruturada (roteiro fixo) ou não estruturada (aberta) |
| **Questionário** | Muitos stakeholders, dispersos geograficamente |
| **Observação / etnografia** | Capta o que o usuário **faz** mas não sabe verbalizar; revela o processo real |
| **Workshop / JAD** | Reunião estruturada com vários stakeholders juntos, decisão rápida |
| **Brainstorming** | Gerar ideias sem julgar na hora |
| **Prototipação** | Requisito vago ou usuário que não sabe o que quer — ele **vê** e reage |
| **Análise de documentos** | Sistema legado, normas, formulários existentes |

> [!tip] Como escolher na questão
> O enunciado dá o **cenário** e você escolhe a técnica:
> muitos e dispersos → **questionário** · não sabem explicar o que fazem →
> **observação** · precisa de consenso rápido entre áreas → **JAD/workshop** ·
> requisito vago, cliente indeciso → **prototipação**.

---

## 5. Validação × Verificação ⭐⭐

> [!danger] Par invertido — verificação × validação
> | | **Verificação** | **Validação** |
> | --- | --- | --- |
> | Pergunta | Estamos construindo o produto **corretamente**? | Estamos construindo o produto **correto**? |
> | Compara com | A especificação | A necessidade real do usuário |
> | Foco | Conformidade interna | Adequação ao uso |
>
> Mnemônico: **V**erificação = conforme a espec**V**. **V**alidação = o usuário
> **V**alidou, é o que ele queria.
> *(Volta no 5.4 aplicado a testes — é o mesmo par.)*

**Técnicas de validação de requisitos:** revisão/inspeção, prototipação,
geração de casos de teste a partir dos requisitos.

---

## 6. Qualidades de um bom requisito ⭐

**Completo · Consistente (sem conflito) · Não ambíguo · Verificável/testável ·
Rastreável · Necessário · Viável · Priorizado**

> [!warning] Verificável é o mais cobrado
> "O sistema deve ser rápido" é **ruim** — não é verificável.
> "O sistema deve responder em até 2 segundos" é **bom**.

---

## 7. Gerenciamento de requisitos ⭐

Duas atribuições, só essas duas:

### 7.1 Controle de mudanças
Requisitos mudam — é inevitável. O processo:
**solicitação → análise de impacto (custo, prazo, requisitos afetados) →
decisão (CCB) → implementação → atualização da documentação.**

**Baseline (linha de base):** versão dos requisitos formalmente aprovada. A partir
dela, qualquer alteração passa pelo controle de mudanças.

### 7.2 Rastreabilidade ⭐
Capacidade de seguir a vida de um requisito nos dois sentidos.

| Tipo | Liga |
| --- | --- |
| **Para trás (backward)** | Requisito → sua **origem** (quem pediu, qual necessidade) |
| **Para frente (forward)** | Requisito → **artefatos** que o implementam (projeto, código, teste) |

Instrumento: **matriz de rastreabilidade**. Serve para medir **impacto de mudança**
e provar cobertura.

---

## 8. Priorização

| Técnica | Como |
| --- | --- |
| **MoSCoW** | Must have · Should have · Could have · Won't have |
| **Valor × custo/risco** | Ordena pelo retorno relativo |

---

## 9. Problemas clássicos

| Problema | O que é |
| --- | --- |
| **Volatilidade** | Requisito muda com frequência ao longo do projeto |
| **Ambiguidade** | Permite mais de uma interpretação |
| **Inconsistência** | Dois requisitos se contradizem |
| **Scope creep** | Escopo cresce sem controle, sem passar pelo processo de mudança |
| **Gold plating** | Equipe entrega além do pedido, sem solicitação |
