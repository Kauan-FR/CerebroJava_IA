## O que é 

Sistemas que gerenciam a estrutura e as informações do banco, ele realiza a ligação entre a base de dados e a aplicação do usuário

## Funções

- Transformar e apresentar os dados
- Controlar o acesso de multiusuário
- prover interfaces de comunicação do banco de dado
- Permite a criação de estruturas de dados
- A manutenção de dados
- Gerenciamento de transações
- Extração de informações

## View (visão)

Conceito que permite que os diferentes usuários compartilhem dados e recursos de processamento

## Sistema de gerenciamento de banco de dados relacional (SGBDR)

É a maneira de representar dados em tabelas. Cada linha na tabela é um registo. As colunas da tabela contêm atributos dos dados e cada registro geralmente tem um valor para cada atributo

## Sistema de gerenciamento de banco de dados não relacional (SGBD NoSQL)

Sistema o qual os atributos não se relacionam entre si. Sistema para documentação de dados

## Classificações do NoSQL

Classificação dos modelos existentes em NoSQL de acordo com a estrutura que os dados são armazenados

- orientado a chave-valor
- orientado a documentos
- orientado a colunas
- orientado a grafos

## ACID (SGBDR)

- Atomicidade
- Consistência
- Isolamento
- Durabilidade

Atomicidade => Todo resultado que são executados ou dão certo, ou por causa de um todos dão erro
Consistência => Respeitar as regras de integridade dos dados, fazendo com que todos as transições sejam consistentes, sem irregularidade
Isolamento => Evitar que transações paralelas interfiram umas nas outras
Durabilidade => Persistência dos efeitos de uma transação no banco de dados em caso de sucesso, mesmo com queda de energia, erros ou travamentos

## Teorema CAP (SGBD NoSQL)

Consiste em um conjunto de requisitos para sistemas distribuídos:
- consistência (consistency)
- disponibilidade (availability)
- tolerância à partição (partition tolerance)

Consistência => Refere-se ao aspecto que todos os nós do sistema devem conter os mesmos dados, garantindo que diferentes usuários terão a mesma visão do estado dos dados
Disponibilidade => O sistema tem que responder a uma requisição mesmo que não esteja consistente
Tolerância à partição => Garantir que o sistema continuará em operação mesmo que algum servidor dos cluster venha a falhar

# 1.13 / 1.14 / 1.18 — SGBD, ACID, NoSQL

## O que é SGBD

Software que gerencia a estrutura e o acesso ao banco, fazendo a ponte entre os
dados armazenados e as aplicações.

### Funções principais

Controle de acesso multiusuário, gerência de transações, controle de concorrência,
segurança e permissões, backup e recuperação, integridade, otimização de consultas,
independência de dados.

### Componentes que caem

| Componente | O que é |
| --- | --- |
| **Catálogo / dicionário de dados** | Guarda os metadados (estrutura) |
| **Processador de consultas** | Interpreta e otimiza o SQL |
| **Gerenciador de transações** | Garante ACID |
| **Gerenciador de armazenamento** | Controla como o dado fica no disco |

### View (visão)

**Tabela virtual** — uma consulta salva com nome, que **não armazena dado próprio**.
Monta o resultado na hora.

Serve para: simplificar consultas complexas, restringir acesso (mostrar só algumas
colunas) e dar **independência lógica** (mudar a estrutura sem quebrar a aplicação).

> View comum = calcula na hora · **View materializada** = guarda o resultado (mais
> rápido, mas pode ficar desatualizado)

## Níveis ANSI/SPARC ⭐

Arquitetura de três esquemas que dá a independência de dados:

| Nível | O que descreve | Quem vê |
| --- | --- | --- |
| **Externo** | Visões — recortes por usuário | Usuário final |
| **Conceitual** | Estrutura lógica completa | Projetista |
| **Interno** | Como o dado é fisicamente armazenado | SGBD |

Ligação com independência → [[1-01-modelagem-conceitual-logica-fisica]]
- Independência **lógica**: entre externo e conceitual
- Independência **física**: entre conceitual e interno

## ACID — transações no SGBD relacional ⭐

| Propriedade | Garante |
| --- | --- |
| **Atomicidade** | Ou tudo executa, ou nada. Não existe "meio feito" |
| **Consistência** | A transação leva o banco de um estado válido a outro, respeitando as regras de integridade |
| **Isolamento** | Transações paralelas não interferem umas nas outras |
| **Durabilidade** | Efeito confirmado (`COMMIT`) persiste mesmo com queda de energia |

Ligação com transações → [[1-16-transacoes]] e TCL → [[1-10-sql]]

## NoSQL — 1.18

Bancos que **não usam o modelo relacional**. Abrem mão de tabelas rígidas e esquema
fixo em troca de **escala horizontal** e flexibilidade. Esquema flexível (schema-on-read).

### Os quatro modelos ⭐

| Modelo | Estrutura | Quando usar |
| --- | --- | --- |
| **Chave-valor** | Par chave → valor. O mais simples | Cache, sessão. Ex.: Redis |
| **Documento** | Documentos JSON/BSON, aninhados | Catálogo, perfil. Ex.: MongoDB |
| **Colunar** (família de colunas) | Colunas agrupadas, otimizado para leitura de muitas linhas | Big data, série temporal. Ex.: Cassandra |
| **Grafo** | Nós e arestas | Rede social, recomendação. Ex.: Neo4j |

> [!warning] Grafo é o único focado em relacionamento
> "NoSQL não tem relacionamento" é falso — grafo existe justamente para isso.

## BASE — o oposto do ACID ⭐

Modelo de consistência dos bancos NoSQL distribuídos:

| BASE | Significa |
| --- | --- |
| **B**asically **A**vailable | O sistema sempre responde |
| **S**oft state | O estado pode mudar sem entrada nova (por propagação) |
| **E**ventually consistent | A consistência é atingida **com o tempo**, não na hora |

> [!danger] ACID × BASE
> **ACID** — consistência **imediata**, prioriza correção. Relacional.
> **BASE** — consistência **eventual**, prioriza disponibilidade. NoSQL distribuído.

---

## Teorema CAP ⭐

Em um sistema distribuído, só dá para garantir **dois dos três**:

| Letra | Garante |
| --- | --- |
| **C** — Consistency | Todos os nós veem o mesmo dado ao mesmo tempo |
| **A** — Availability | O sistema sempre responde a uma requisição |
| **P** — Partition tolerance | Continua funcionando mesmo se a rede entre nós falhar |

> [!danger] A regra do CAP
> Como partição de rede **sempre pode acontecer**, na prática você escolhe entre
> **CP** (sacrifica disponibilidade) ou **AP** (sacrifica consistência).
> O "CA" puro não existe em sistema distribuído real.

> [!warning] Consistência do CAP ≠ consistência do ACID
> **CAP** — todos os nós com o mesmo dado (é sobre **distribuição**)
> **ACID** — respeitar regras de integridade (é sobre **a transação**)
> Mesmo nome, conceitos diferentes. A banca cobra isso.
