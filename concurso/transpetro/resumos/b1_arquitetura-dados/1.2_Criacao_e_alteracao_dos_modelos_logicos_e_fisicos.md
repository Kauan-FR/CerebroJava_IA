### Relação 1:1 (dois lados obrigatorios)

Quado existe duas obrigatoriedades na relação entre dois mínimos, obrigatoriamente essas duas tabelas elas se tornam uma única entidade, onde os atributos das duas irão se juntar em uma única tabela.

### Relação 1:1 (um lado obrigatorio)

Quando acontece de um dos lados serem obrigatórios e o outro ser opcional `0:1`, nos repetimos os mesmo atributos das tabelas em duas entidades, passando a chave primaria (PK) da tabela que possui a obrigatoriedade para a tabela que é opcional. E caso tenha um atributo que faz parte da relação, ele também para para a tabela que esta a chave FK

## Relação 1:1 (ambos os lados opcionais `0:1`)

Quando acontece de ambos os lados serem opcionais `0:1`, se repete as mesmas tabelas com os mesmo atributos, mas é criado uma terceira tabela, uma tabela associativa, onde ambas as chaves primárias das duas tabelas vão para essa tabela associativa, tornando assim essas duas FK que estão na tabela associativa como PKs dessa tabela.

## Relação 1:N

Nessa relação também se repete as duas tabelas com os mesmos atributos, a tabela que possui a cardinalidade máxima em muitos `N`, recebe a chave estrangeira da outra tabela.

## Relação N:N

Nessa relação, quando ambas as cardinalidades são muitos para muitos, transforma essas duas tabelas em duas entidades repetindo os mesmos atributos, e criando uma terceira tabela para associar essas duas tabelas, ambas as chaves primarias das duas tabelas migram para essa tabela associativa, transformando as em chaves estrangeiras, e cria se também uma chave primeira para essa tabela associativa

# 1.2 Criação e alteração dos modelos lógico e físico

## Conceitual -> Lógico

É basicamente transformar as informações que estão no modelo conceitual para o lógico.

> [!warning] Vocabulário
> No conceitual existe **entidade**. No lógico existe **tabela**.
> Duas entidades no conceitual → duas tabelas no lógico.
> A notação correta é **N:M** (ou M:N), nunca `N:N`.

### Ordem do mapeamento

1. Cada entidade → uma tabela
2. Atributos simples → colunas
3. Atributos compostos → decompor em colunas
4. Atributos multivalorados → tabela própria
5. Atributos derivados → normalmente **não** viram coluna (calculados na consulta)
6. Identificador → PK
7. Relacionamentos → conforme a cardinalidade
8. Entidade fraca → PK composta
9. Especialização → uma das três estratégias

---

## Relação 1:1 (dois lados obrigatórios)

Quando existe obrigatoriedade nos dois mínimos, as duas entidades se tornam **uma tabela só**, onde os atributos das duas se juntam.

> [!note] É a opção preferencial, não obrigatória
> Ainda é possível manter duas tabelas com FK + `UNIQUE` + `NOT NULL`.
> Se uma das entidades tiver relacionamentos próprios com outras, fundir quebra esses relacionamentos.
>
> Banca: "a mais adequada" → fundir. "É obrigatório fundir" → **falso**.

## Relação 1:1 (um lado obrigatório)

Quando um dos lados é obrigatório e o outro é opcional `(0,1)`, mantêm-se as duas tabelas com seus atributos, e a **PK do lado opcional vira FK na tabela do lado obrigatório**.

Atributo do relacionamento vai junto, para a tabela que recebeu a FK.

```sql
Cracha(id, codigo, id_empregado UNIQUE NOT NULL)   -- FK aqui
```

**Por quê:** todo crachá tem empregado (participação total), então a FK **nunca fica nula**. Se ficasse no Empregado, toda linha sem crachá teria coluna nula.

> [!danger] O UNIQUE é obrigatório
> Sem `UNIQUE`, isso vira 1:N. É a constraint que garante o 1:1.

## Relação 1:1 (ambos os lados opcionais)

Quando ambos os lados são `(0,1)`, mantêm-se as duas tabelas e cria-se uma **terceira, associativa**, para onde migram as PKs das duas.

```sql
Alocacao(id_empregado UNIQUE, id_veiculo UNIQUE)
```

> [!danger] Cada FK precisa de UNIQUE separado
> A PK **não** é a composição das duas. Com PK composta, o mesmo empregado poderia
> aparecer em várias linhas com veículos diferentes — isso permitiria 1:N.
> Uma das FKs pode ser PK, mas a outra ainda precisa do seu próprio `UNIQUE`.

> [!note] A associativa aqui é opcional
> É a única cardinalidade em que dá para escolher: FK direta também resolve.
> A associativa evita nulos, mas custa um join.
> Banca: "é possível resolver sem tabela adicional" → **verdadeiro**.

## Relação 1:N

Mantêm-se as duas tabelas com seus atributos. A tabela que possui a cardinalidade máxima **muitos (N)** recebe a chave estrangeira da outra.

```sql
Departamento(id, nome)
Empregado(id, nome, id_departamento)   -- FK aqui
```

**Por quê:** se a FK ficasse no lado 1, o Departamento teria que guardar vários ids numa coluna — a **1FN proíbe** atributo multivalorado.

| Participação do lado N | Coluna FK |
| --- | --- |
| Total `(1,n)` | `NOT NULL` |
| Parcial `(0,n)` | aceita nulo |

Variação: se a participação do lado N for parcial e rara, pode-se usar tabela associativa para evitar mar de nulos. É opção, não regra.

## Relação N:M

Quando ambas as cardinalidades são muitos para muitos, as duas entidades viram duas tabelas com seus atributos, e cria-se uma **terceira tabela associativa**. As PKs das duas migram para ela como FKs.

```sql
Autor(id_autor, nome)
Livro(id_livro, titulo)
Autoria(id_autor, id_livro)
PRIMARY KEY (id_autor, id_livro)
```

> [!danger] Não se cria chave nova
> A PK da associativa **é a composição das duas FKs**.
> PK artificial (`id_autoria`) funciona na prática, mas exige `UNIQUE(id_autor, id_livro)`
> — sem isso, o mesmo autor entra duas vezes no mesmo livro.
> Na teoria clássica e na prova: **PK composta**.

Atributo do relacionamento (nota, data, quantidade) vira **coluna da tabela associativa**.

## Entidade fraca

A PK da fraca é **composta**: chave da forte + chave parcial.

```sql
Segurado(num_apolice PK, nome)
Dependente(num_apolice FK, nome, ...)
PRIMARY KEY (num_apolice, nome)
```

A FK leva `ON DELETE CASCADE` — se o segurado some, os dependentes somem junto, porque não existem sem ele.

## Atributos multivalorado e composto

**Multivalorado → tabela nova.** Não pode ficar como coluna; a 1FN proíbe.

```sql
Telefone(id_cliente FK, numero)
PRIMARY KEY (id_cliente, numero)
```

**Composto → várias colunas.**

endereço → logradouro, numero, bairro, cidade, cep

> [!warning] Par que a banca inverte
> Composto **decompõe em colunas** · Multivalorado **vira tabela**

## Relacionamento ternário

Vira tabela associativa com **três** FKs.

```sql
Fornecimento(id_fornecedor, id_produto, id_projeto, quantidade)
PRIMARY KEY (id_fornecedor, id_produto, id_projeto)
```

## Autorrelacionamento 1:N

Vira FK apontando para a própria tabela. A coluna aceita nulo — o presidente não tem supervisor.

```sql
Empregado(id PK, nome, id_supervisor FK -> Empregado.id)
```

## Lógico -> Físico

É transformar o modelo lógico em algo executável no SGBD escolhido.

- Escolher o **tipo de dado real**: `VARCHAR(100)`, `NUMERIC(10,2)`, `DATE`
- Definir constraints: `NOT NULL`, `CHECK`, `DEFAULT`, `UNIQUE`
- Decidir índices, partições, tablespaces
- Gerar o **DDL** executável

É o único nível que **depende do SGBD**.

## Alteração de esquema

A segunda metade do subtópico — o que acontece quando o modelo já existe e muda.

- `ALTER TABLE ADD COLUMN` em tabela com dados → precisa aceitar nulo ou ter `DEFAULT`
- Adicionar FK quando já existem linhas que violam a regra → falha
- Mudar tipo de coluna → risco de perder dado

> [!warning] Par invertido
> **Forward engineering** = modelo → banco
> **Reverse engineering** = banco → modelo (item 1.9)

## Resumo de cardinalidade

| Relação | Solução |
| --- | --- |
| 1:1 obrigatório-obrigatório | **funde** em uma tabela |
| 1:1 obrigatório-opcional | FK no lado **obrigatório** + `UNIQUE` |
| 1:1 opcional-opcional | associativa, `UNIQUE` nas **duas** FKs |
| 1:N | FK no lado **N** |
| N:M | 3 tabelas, PK = as duas FKs |
| Ternário | associativa com 3 FKs |
| Autorrelacionamento | FK para a própria tabela |
| Entidade fraca | PK composta (forte + parcial) |
| Multivalorado | tabela nova |
| Composto | várias colunas |
