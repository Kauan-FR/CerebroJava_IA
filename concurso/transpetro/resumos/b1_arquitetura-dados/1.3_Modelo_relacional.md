## O que é

Modelo de dados proposto por **Edgar F. Codd (1970)**, baseado em **teoria dos
conjuntos e lógica de predicados**. Representa os dados como um conjunto de
**relações**.

> [!danger] "Relacional" NÃO vem de relacionamento entre tabelas
> Vem de **relação**, o nome matemático da tabela.
> Duas tabelas sem nenhuma FK continuam sendo modelo relacional.

## Vocabulário formal × prático

| Formal (teoria) | Prático (SQL) |
| --- | --- |
| Relação | Tabela |
| Tupla | Linha / registro |
| Atributo | Coluna / campo |
| Domínio | Tipo de dado |
| Esquema da relação | Estrutura (nome + atributos) |
| Instância | Conteúdo em um dado momento |

> [!warning] Par que a banca inverte
> **Grau** = nº de atributos (colunas)
> **Cardinalidade** = nº de tuplas (linhas)

## Propriedades da relação

- **Não há tuplas duplicadas** — a relação é um conjunto
- **Ordem das tuplas é irrelevante**
- **Ordem dos atributos é irrelevante**
- **Todo valor é atômico** — sem multivalorado nem composto, **ou é ou não é** (isso é a 1FN)

## Chaves

| Chave | O que é |
| --- | --- |
| Superchave | Qualquer conjunto que identifica unicamente |
| **Candidata** | Superchave **mínima** (sem atributo dispensável) |
| **Primária** | A candidata **escolhida** |
| **Alternativa** | As candidatas não escolhidas |
| **Estrangeira** | Atributo que **referencia** a PK de outra relação |

FK **não** é atributo derivado — derivado é atributo calculado.
PK **não** é necessariamente gerada pelo SGBD — isso descreve chave substituta.

## Regras de integridade

| Integridade | Regra |
| --- | --- |
| **De domínio** | Todo valor pertence ao domínio do atributo |
| **De entidade** | A PK **não pode ser nula** |
| **Referencial** | Toda FK aponta para uma PK existente **ou é nula** |

Integridade de entidade é o motivo de PK não aceitar nulo.
Referencial → ver [[1.5_Integridade_referencial]]

## Modelo Entidade-Relacionamento (MER)

Modelo **conceitual** criado por **Peter Chen (1976)**.
O **diagrama ER** é a sua representação gráfica — não é etapa posterior.

| Componente | O que é |
| --- | --- |
| **Entidade** | Objeto do mundo real com existência independente, sobre o qual se armazena informação |
| **Atributo** | Característica que descreve a entidade |
| **Relacionamento** | Associação lógica entre entidades |

> [!warning] MER × Relacional
> **MER** é conceitual, independe de SGBD, tem entidade e relacionamento.
> **Relacional** é lógico, tem relação, tupla e atributo.
> O MER **é transformado** no relacional → ver [[1.2_Criacao_e_alteracao_dos_modelos_logicos_e_fisicos]]

## Análise de requisitos

**Fase** que define quais dados serão armazenados e quais serão descartados.
Evita redundância e armazenamento de informação inútil.
Antecede a modelagem conceitual.

## Álgebra relacional (base do SQL)

| Operação | O que faz | SQL |
| --- | --- | --- |
| Seleção (σ) | Filtra **tuplas** (linhas) | `WHERE` |
| Projeção (π) | Filtra **atributos** (colunas), elimina duplicadas | `SELECT DISTINCT col` |
| Produto cartesiano (×) | Cada linha de uma com cada linha da outra | `CROSS JOIN` |
| Junção (⋈) | Produto cartesiano **+** seleção | `INNER JOIN`, `NATURAL JOIN` |
| Junção externa (⟕ ⟖ ⟗) | Junção preservando linhas sem correspondente | `LEFT` / `RIGHT` / `FULL [OUTER] JOIN` |
| União (∪) | Empilha tuplas das duas, sem repetir | `UNION` |
| Interseção (∩) | Tuplas presentes nas duas | `INTERSECT` |
| Diferença (−) | Tuplas da primeira que não estão na segunda | `EXCEPT` |
| Renomeação (ρ) | Renomeia relação e atributos | alias / `AS` |
| Divisão (÷) | Quais elementos de A se relacionam com **todos** de B | `NOT EXISTS` aninhado |

> [!warning] Par que a banca inverte
> **Seleção σ = linhas (tuplas)** · **Projeção π = colunas (atributos)**

União, interseção e diferença exigem **compatibilidade de união**: mesmo número
de atributos e domínios correspondentes.

Junção é **operação de consulta**, não é o relacionamento em si.
### Exemplos

#### Chave estrangeira (FK) -> `FOREIGN KEY`

```
Departamentos (ID_Departamento, Nome, Localizacao)
Professores   (ID_Professor, Nome, ID_Departamento)
Alunos        (ID_Aluno, Nome, ID_Professor_Orientador)
```

As restrições que o enunciado exigia: todo professor pertence a um departamento, e alunos podem ser orientados por professores. A resposta correta (alternativa B) era a única que declarava as duas chaves estrangeiras:

Estrutura do banco:

**Departamento:**

| ID_Departamento | Nome       | Localizacao |
| --------------- | ---------- | ----------- |
| 10              | Computação | Bloco A     |
| 20              | Matemática | Bloco B     |
| 30              | Física     | Bloco C     |

**Professores:**

| ID_Professor | Nome  | ID_Departamento |
| ------------ | ----- | --------------- |
| 1            | Ana   | 10              |
| 2            | Bruno | 20              |
| 3            | Carla | 10              |


**Alunos:**

| ID_Aluno | Nome   |
| -------- | ------ |
| 100      | Daniel |
| 101      | Elisa  |
| 102      | Fabio  |

A consulta:

```sql
CREATE TABLE Professores (
   ID_Professor INT PRIMARY KEY,
   Nome VARCHAR(100),
   ID_Departamento INT,
   FOREIGN KEY (ID_Departamento) REFERENCES Departamentos(ID_Departamento)
);
```

| ID_Aluno | Nome   | ID_Professor_Orientador |
| -------- | ------ | ----------------------- |
| 100      | Daniel | 1                       |
| 101      | Elisa  | 3                       |
| 102      | Fabio  | _(nulo)_                |

#### Seleção (σ) -> `WHERE`

Modelo lógico - de onde parte:

`Professores (ID_Professor, Nome, ID_Departamento)`

Modelo físico - a consulta:

```sql
SELECT * FROM Professores WHERE ID_Departamento = 10;
```

Álgebra - `σ ID_Departamento = 10 (Professores)`

Modelo lógico - como ficou:

| ID_Professor | Nome  | ID_Departamento |
| ------------ | ----- | --------------- |
| 1            | Ana   | 10              |
| 3            | Carla | 10              |

O que aconteceu:
- 3 colunas continuam 3 colunas. 3 linhas viraram 2. O filtro foi horizontal. O `WHERE` testa cada linha e descarta quem não passa. Bruno saio porque é do depto 20.

#### Projeção (π) -> `SELECT`

Modelo logico - de onde parte:

`Professores` - 3 linhas, 3 colunas

Modelo físico - a consulta:

```sql
SELECT DISTINCT Nome, ID_Departamento FROM Professores;
```

Álgebra - `π Nome, ID_Departamento (Professores)`

Modelo lógico - como ficou:

| Nome  | ID_Departamento |
| ----- | --------------- |
| Ana   | 10              |
| Bruno | 20              |
| Carla | 10              |
O que aconteceu:
- 3 linhas continuam, 3 colunas viraram 2. O corte foi vertical. `ID_Professor` desapareceu.

Se projetasse só o `ID_Departamento` o resultado tem 2 linhas (10 e 20), não 3, a projeção elimina duplicadas. É por isso que o `DISTINCT` está ali: sem ele, o SQL devolveria 3 linhas e não seria projeção pura.

#### Seleção + projeção combinadas

Modelo físico — a consulta

```sql
SELECT Nome FROM Professores WHERE ID_Departamento = 10;
```

Álgebra: `π Nome (σ ID_Departamento = 10 (Professores))`

**Modelo lógico — como ficou**

|Nome|
|---|
|Ana|
|Carla|

**O que aconteceu:**
- Cortou nas duas direções. Primeiro filtrou linhas (σ, o `WHERE`), depois selecionou colunas (π, a lista do `SELECT`).

**A ordem importa e cai em prova:** o otimizador aplica a seleção **antes** da projeção, ainda que o `SELECT` venha escrito primeiro. Reduzir de 3 para 2 linhas antes de mexer nas colunas é mais barato do que o contrário. Isso é o "empurrar a seleção para baixo na árvore de consulta" — conceito da questão 51 da prova real de 2023, sobre o otimizador de consultas.

#### Produto cartesiano (×) -> `CROSS JOIN`

Modelo físico — a consulta

```sql
SELECT * FROM Professores, Departamentos;
```

Álgebra: `Professores × Departamentos`

**Modelo lógico — como ficou (9 linhas)**

| ID_Professor | Nome  | ID_Departamento | ID_Departamento | Nome       |
| ------------ | ----- | --------------- | --------------- | ---------- |
| 1            | Ana   | 10              | 10              | Computação |
| 1            | Ana   | 10              | 20              | Matemática |
| 1            | Ana   | 10              | 30              | Física     |
| 2            | Bruno | 20              | 10              | Computação |
| ...          |       |                 |                 |            |
**O que aconteceu:**
- Cada linha de uma combinou com cada linha da outra. 3 × 3 = 9.

**Os dois números que a banca pede:**
- **Grau** (colunas) = soma: 3 + 3 = **6**
- **Cardinalidade** (linhas) = produto: 3 × 3 = **9**

Repare que a linha "Ana / Matemática" é **falsa** — Ana é do depto 10. O produto cartesiano não valida nada. Esquecer o `WHERE` numa consulta com duas tabelas produz exatamente isto, e é o erro clássico que a banca ilustra.

#### Junção (⋈) -> `INNER JOIN`, `NATURE JOIN` e `JOIN`

Modelo físico — a consulta

```sql
SELECT P.Nome, D.Nome AS Departamento
FROM   Professores P
INNER JOIN Departamentos D ON P.ID_Departamento = D.ID_Departamento;
```

Álgebra: `π ... (Professores ⋈ Departamentos)`

**Modelo lógico — como ficou**

|Nome|Departamento|
|---|---|
|Ana|Computação|
|Bruno|Matemática|
|Carla|Computação|

 **O que aconteceu:** das 9 combinações do produto cartesiano, sobraram as 3 que satisfazem a condição. **Junção = produto cartesiano + seleção.** É literalmente isso — o SGBD pode até executar assim internamente.

**Repare no que sumiu:** o departamento Física (30) não aparece. Ele não tem professor, então nenhuma combinação passou no filtro. `INNER JOIN` descarta quem não casa dos **dois** lados.

**Junção natural × equijunção — cai como distrator:**

| | Condição | Coluna repetida |
| --- | --- | --- |
| **Natural** (⋈) | Automática, por **todas** as colunas de mesmo nome | **Elimina** a duplicada |
| **Equijunção** | Você escreve, com `=` | **Mantém** as duas |

> [!warning] Perigo do NATURAL JOIN
> Ele junta por **todas** as colunas homônimas. Se as duas tabelas tiverem
> `Nome` e `ID_Departamento` com o mesmo nome, ele junta pelas duas — e o
> resultado não é o esperado. Por isso é evitado na prática, e por isso a banca gosta.

> [!note] Por que ρ existe
> No resultado acima há duas colunas `Nome` e duas `ID_Departamento`.
> Sem renomear, não há como referenciar uma sem ambiguidade.
> É a mesma razão dos apelidos `f1` e `f2` na autojunção.


#### Junção externa (⟕ ⟖) -> `LEFT JOIN`, `RIGHT JOIN`, `FULL JOIN` e `OUTER JOIN`

```sql
SELECT D.Nome AS Departamento, P.Nome AS Professor
FROM   Departamentos D
LEFT JOIN Professores P ON D.ID_Departamento = P.ID_Departamento;
```

**Modelo lógico — como ficou**

|Departamento|Professor|
|---|---|
|Computação|Ana|
|Computação|Carla|
|Matemática|Bruno|
|Física|_(nulo)_|
**O que aconteceu:** a Física voltou, com nulo no lado que não tem correspondente. O `LEFT JOIN` preserva **tudo da tabela à esquerda**, case ou não.

**Quando usar cada uma:**

- Pergunta "quais professores estão em qual departamento" → `INNER JOIN`
- Pergunta "quais departamentos **não têm** professor" → `LEFT JOIN` + `WHERE P.ID_Professor IS NULL`

O segundo caso é a aplicação mais cobrada da junção externa: encontrar **ausência**.

Isso liga com a tabela Alunos: o Fabio tem orientador nulo. Se você fizer `INNER JOIN` entre Alunos e Professores, o Fabio **desaparece** do resultado. Com `LEFT JOIN`, ele aparece com orientador nulo. Essa é a diferença que resolve metade das questões de junção.

#### Autojunção — esta caiu literalmente

**Questão 49 da prova de 2023.** A tabela era esta:

Familia

| Pai    | Filho   |
| ------ | ------- |
| Andre  | Carlos  |
| Andre  | Claudio |
| Bruno  | Diego   |
| Bruno  | Daniel  |
| Carlos | Eriko   |
| Carlos | Fabio   |
| Daniel | Gustavo |
| Diego  | Heleno  |
| Eriko  | Isidoro |
| Fabio  | João    |
**A pergunta:** qual SQL retorna os **netos** de Carlos (Isidoro e João)?

Modelo físico — a consulta correta

```sql
SELECT f2.filho
FROM   Familia f1 INNER JOIN Familia f2 ON f1.filho = f2.pai
WHERE  f1.pai = 'Carlos';
```

**Como se resolve, passo a passo:**

1. `f1` com `pai = 'Carlos'` → filhos: **Eriko, Fabio**
2. A condição `f1.filho = f2.pai` pega essas linhas e procura em `f2` quem tem **Eriko** ou **Fabio** como pai
3. `f2` devolve: Eriko→**Isidoro**, Fabio→**João**
4. `SELECT f2.filho` → **Isidoro, João** ✓

**O que é autojunção:** a mesma tabela entra duas vezes na consulta, com apelidos diferentes (`f1`, `f2`). Em álgebra relacional isso exige o operador de **renomeação (ρ)** — é a razão de ρ existir. Sem renomear, você não consegue distinguir uma cópia da outra.

Isto é o **autorrelacionamento** do modelo conceitual chegando ao físico. Pai/Filho é a entidade Pessoa se relacionando com ela mesma; no SQL vira autojunção.

**Como os distratores foram construídos** — vale estudar isso, porque é o padrão da banca:

| Alt. | O que muda                              | Efeito                       |
| ---- | --------------------------------------- | ---------------------------- |
| (A)  | `f1.filho = f2.pai`, retorna `f2.filho` | ✓ desce dois níveis          |
| (B)  | condição invertida, retorna `f1.pai`    | sobe em vez de descer        |
| (C)  | condição certa, mas retorna `f1.pai`    | devolve 'Carlos'             |
| (D)  | `f1.pai = f2.pai`                       | junta irmãos, não netos      |
| (E)  | `f1.filho = f2.filho`                   | linha consigo mesma → filhos |

#### União e diferença

```sql
SELECT Nome FROM Professores
UNION
SELECT Nome FROM Alunos;
```

**O que aconteceu:** empilhou as linhas das duas, eliminando repetidas. Exige **compatibilidade**: mesmo número de colunas e tipos correspondentes. `SELECT Nome` de um lado e `SELECT Nome, Localizacao` do outro dá erro.

```sql
SELECT Nome FROM Departamentos
EXCEPT
SELECT D.Nome FROM Departamentos D
       JOIN Professores P ON D.ID_Departamento = P.ID_Departamento;
```

Resultado: **Física**. Departamentos que existem menos os que têm professor.

**A diferença não é comutativa.** Inverter os dois blocos muda o resultado. Já foi cobrado.

#### Divisão (÷) -> `NOT EXISTS`

Não tem operador SQL. Aparece quando o enunciado diz **"todos os"**.

_"Quais alunos cursaram todas as disciplinas obrigatórias?"_

```sql
SELECT A.Nome FROM Alunos A
WHERE NOT EXISTS (
    SELECT 1 FROM Obrigatorias O
    WHERE NOT EXISTS (
        SELECT 1 FROM Cursou C
        WHERE C.ID_Aluno = A.ID_Aluno AND C.ID_Disciplina = O.ID_Disciplina
    )
);
```

Leia de dentro pra fora: _"não existe disciplina obrigatória que este aluno não tenha cursado"_. Dupla negação = quantificador universal.

**Na prova, o que cai é o reconhecimento**, não a escrita: viu "todos/todas", pensou divisão.
