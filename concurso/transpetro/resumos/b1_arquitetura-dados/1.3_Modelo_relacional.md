## O que é

Modelo de dados proposto por **Edgar F. Codd (1970)**, baseado em **teoria dos
conjuntos e lógica de predicados**. Representa os dados como um conjunto de
**relações**.

> [!danger] "Relacional" NÃO vem de relacionamento entre tabelas
> Vem de **relação**, o nome matemático da tabela.
> Duas tabelas sem nenhuma FK continuam sendo modelo relacional.

## Vocabulário formal × prático

| Formal (teoria) | Prático (SQL) |
| --- | --- |
| Relação | Tabela |
| Tupla | Linha / registro |
| Atributo | Coluna / campo |
| Domínio | Tipo de dado |
| Esquema da relação | Estrutura (nome + atributos) |
| Instância | Conteúdo em um dado momento |

> [!warning] Par que a banca inverte
> **Grau** = nº de atributos (colunas)
> **Cardinalidade** = nº de tuplas (linhas)

## Propriedades da relação

- **Não há tuplas duplicadas** — a relação é um conjunto
- **Ordem das tuplas é irrelevante**
- **Ordem dos atributos é irrelevante**
- **Todo valor é atômico** — sem multivalorado nem composto, **ou é ou não é** (isso é a 1FN)

## Chaves

| Chave | O que é |
| --- | --- |
| Superchave | Qualquer conjunto que identifica unicamente |
| **Candidata** | Superchave **mínima** (sem atributo dispensável) |
| **Primária** | A candidata **escolhida** |
| **Alternativa** | As candidatas não escolhidas |
| **Estrangeira** | Atributo que **referencia** a PK de outra relação |

FK **não** é atributo derivado — derivado é atributo calculado.
PK **não** é necessariamente gerada pelo SGBD — isso descreve chave substituta.

## Regras de integridade

| Integridade | Regra |
| --- | --- |
| **De domínio** | Todo valor pertence ao domínio do atributo |
| **De entidade** | A PK **não pode ser nula** |
| **Referencial** | Toda FK aponta para uma PK existente **ou é nula** |

Integridade de entidade é o motivo de PK não aceitar nulo.
Referencial → ver [[1.5_Integridade_referencial]]

## Modelo Entidade-Relacionamento (MER)

Modelo **conceitual** criado por **Peter Chen (1976)**.
O **diagrama ER** é a sua representação gráfica — não é etapa posterior.

| Componente | O que é |
| --- | --- |
| **Entidade** | Objeto do mundo real com existência independente, sobre o qual se armazena informação |
| **Atributo** | Característica que descreve a entidade |
| **Relacionamento** | Associação lógica entre entidades |

> [!warning] MER × Relacional
> **MER** é conceitual, independe de SGBD, tem entidade e relacionamento.
> **Relacional** é lógico, tem relação, tupla e atributo.
> O MER **é transformado** no relacional → ver [[1.2_Criacao_e_alteracao_dos_modelos_logicos_e_fisicos]]

## Análise de requisitos

**Fase** que define quais dados serão armazenados e quais serão descartados.
Evita redundância e armazenamento de informação inútil.
Antecede a modelagem conceitual.

## Álgebra relacional (base do SQL)

| Operação                       | O que faz                                                                                                                     |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Seleção (σ)                    | Filtra **tuplas** (linhas) → `WHERE`                                                                                          |
| Projeção (π)                   | Filtra **atributos** (colunas) → `SELECT col`                                                                                 |
| Junção (⋈)                     | Combina relações por atributo comum → `INNER JOIN`, `NATURE JOIN` e `JOIN`                                                    |
| Junção externas (⟕ ⟖ ⟗)        | Combina relações (tabelas) preservando as linhas sem correspondentes -> `LEFT JOIN`, `RIGHT JOIN`, `FULL JOIN` e `OUTER JOIN` |
| União / Interseção / Diferença | Operações de conjunto                                                                                                         |
| Produto cartesiano (×)         | Todas as combinações                                                                                                          |
| Renomeação (ρ)                 | Usado para trocar o nome da relação(tabela) e de suas colunas(atributos) -> `AS`                                              |
| União (∪)                      | Junta as linhas (tuplas) de duas tabelas, sem repetir, elas precisam ser compatíveis -> `UNION`                               |
| Interseção (∩)                 | Linhas que estão nas duas tabelas, também precisa de compatibilidade -> `INTERSECT`                                           |
| Diferença (— −)                | Linhas que estão na primeira e não na segunda, também exige compatibilidade -> `EXCEPT`                                       |
| Produto cartesiano (×)         | Combina cada linha (tupla) de uma com cada linha de outra -> `CROSS JOIN`                                                     |
| Divisão (÷)                    | Filtra **todas** linhas e colunas com base no que é exigido -> `NOT EXISTS`                                                   |

> [!warning] Par que a banca inverte
> **Seleção = linhas(tuplas)** · **Projeção = colunas(atributos)**

Junção é **operação de consulta**, não é o relacionamento em si.

### Exemplos

#### Chave estrangeira (FK) -> `FOREIGN KEY`

```
Departamentos (ID_Departamento, Nome, Localizacao)
Professores   (ID_Professor, Nome, ID_Departamento)
Alunos        (ID_Aluno, Nome, ID_Professor_Orientador)
```

As restrições que o enunciado exigia: todo professor pertence a um departamento, e alunos podem ser orientados por professores. A resposta correta (alternativa B) era a única que declarava as duas chaves estrangeiras:

Estrutura do banco:

**Departamento:**

| 10              | Computação | Bloco A     |
| 20              | Matemática | Bloco B     |
| 30              | Física     | Bloco C     |

**Professores:**

| ID_Professor | Nome  | ID_Departamento |
| ------------ | ----- | --------------- |
| 1            | Ana   | 10              |

**Alunos:**

| ID_Aluno | Nome   |
| -------- | ------ |
| 100      | Daniel |

A consulta:

```sql
CREATE TABLE Professores (
   ID_Professor INT PRIMARY KEY,
   Nome VARCHAR(100),
   ID_Departamento INT,
   FOREIGN KEY (ID_Departamento) REFERENCES Departamentos(ID_Departamento)
```

#### Seleção (σ) -> `WHERE`

Modelo lógico - de onde parte:

`Professores (ID_Professor, Nome, ID_Departamento)`

Modelo físico - a consulta:

```sql
SELECT * FROM Professores WHERE ID_Departamento = 10;
```

Álgebra - `σ ID_Departamento = 10 (Professores)`

Modelo lógico - como ficou:

| ID_Professor | Nome  | ID_Departamento |
| ------------ | ----- | --------------- |
| 1            | Ana   | 10              |
| 3            | Carla | 10              |

O que aconteceu:
- 3 colunas continuam 3 colunas. 3 linhas viraram 2. O filtro foi horizontal. O `WHERE` testa cada linha e descarta quem não passa. Bruno saio porque é do depto 20.

#### Projeção (π) -> `SELECT`

Modelo logico - de onde parte:

`Professores` - 3 linhas, 3 colunas

Modelo físico - a consulta:

```sql
SELECT DISTINCT Nome, ID_Departamento FROM Professores;
```

Álgebra - `π Nome, ID_Departamento (Professores)`

Modelo lógico - como ficou:

| ----- | --------------- |

Não fazem parte da teoria relacional — são recursos do SGBD.
