## O que é

Obter o modelo **lógico** e depois o **conceitual** a partir do banco que já existe.
Percorre o caminho inverso da modelagem.

FÍSICO → LÓGICO → CONCEITUAL


> [!danger] Par que a banca inverte
> **Forward engineering** — modelo → banco (gera o DDL)
> **Reverse engineering** — banco → modelo (gera o diagrama)

**Fonte da informação:** o **catálogo do sistema**, não os dados nem o log.

## Quando se usa

- Sistema legado em produção **sem documentação**
- Documentação existe mas está desatualizada
- Migração de plataforma
- Auditoria e análise de impacto

## Os quatro passos

### Passo 1 — Identificar as entidades

Nem toda tabela é entidade. Uma tabela pode ser:

- Uma entidade
- Um relacionamento N:M
- Uma entidade especializada
- Um atributo multivalorado

**Classificação pela composição da PK** ⭐ — é o que resolve a maioria dos casos:

| Regra | Composição da PK                              | O que a tabela é                                                                  |
| ----- | --------------------------------------------- | --------------------------------------------------------------------------------- |
| **1** | PK composta por **duas ou mais FKs**          | Relacionamento **N:M** (tabela associativa)                                       |
| **2** | PK composta por **uma FK + atributo próprio** | **Entidade fraca** (a FK é o identificador externo, o atributo é a chave parcial) |
| **3** | PK é **inteiramente uma FK**                  | **Entidade especializada** (subclasse)                                            |
| **4** | Demais casos                                  | **Entidade forte**                                                                |

> [!tip] Olhar para a PK resolve a maioria
> O fator determinante é **a composição da chave primária**.

### Passo 2 — Definir os relacionamentos

Toda FK que **não** implementa N:M nem especialização representa um relacionamento
**1:1 ou 1:N**.

> [!warning] A regra não permite dizer qual dos dois
> Para distinguir:
> - **`UNIQUE` na FK** → é 1:1
> - Sem `UNIQUE` → é 1:N
> - Se não houver constraint, é preciso **verificar o conteúdo** do banco

### Passo 3 — Definir os atributos

Cada coluna que **não é FK** vira atributo da entidade correspondente.

> [!warning] FK não vira atributo
> Chave estrangeira corresponde a **relacionamento** no DER, não a atributo.

### Passo 4 — Definir os identificadores

| Coluna da PK | Corresponde a |
| --- | --- |
| **Não é FK** | Identificador **próprio** da entidade |
| **É FK** | Identificador **externo** — vem da entidade forte |

## A ambiguidade fundamental ⭐

O modelo físico **perdeu informação** na ida. A engenharia reversa não recupera tudo:

| Não se recupera | Por quê |
| --- | --- |
| 1:1 × 1:N | Só o `UNIQUE` ou os dados revelam |
| Cardinalidade **mínima** | `NOT NULL` sugere obrigatório, mas não garante |
| Nomes de negócio | `TB01`, `cod_cli` não dizem nada |
| Especialização total × parcial | Não fica registrado no banco |
| Regras que nunca foram implementadas | Existiam só na cabeça do analista |

> [!danger] Engenharia reversa NÃO é automática
> A ferramenta gera um rascunho. O resultado precisa ser **validado com o negócio**
> e enriquecido manualmente.

## Palavras-gatilho

| Enunciado diz                                | É                                |
| -------------------------------------------- | -------------------------------- |
| "obter o modelo a partir do banco existente" | **engenharia reversa**           |
| "gerar o banco a partir do modelo"           | **forward engineering**          |
| "sistema legado sem documentação"            | engenharia reversa               |
| "PK composta por duas FKs"                   | relacionamento **N:M**           |
| "PK é uma FK mais um atributo próprio"       | **entidade fraca**               |
| "PK é inteiramente uma FK"                   | **especialização**               |
| "de onde a ferramenta lê a estrutura"        | **catálogo do sistema**          |
| "otimizar desempenho do banco"               | **tuning** (1.17), não é reversa |
| "corrige e regera"                           | **reengenharia**                 |
| "sincroniza 2 sentidos"                      | **round-trip**                   |

> [!warning] Distratores já vistos
> Já marquei **tuning** achando que era reversa. Tuning é performance, não gera modelo.
> "Refatoração conceitual" **não existe** — termo inventado.

## Os quatro processos ⭐

> [!danger] A banca embaralha os quatro

| Termo | Direção |
| --- | --- |
| **Engenharia reversa** | banco → modelo |
| **Engenharia direta** (forward) | modelo → banco |
| **Reengenharia** | banco → modelo → **ajuste** → banco novo |
| **Round-trip** | sincronização **contínua nos dois sentidos** |

**Gatilhos:**
- "obter o modelo do banco existente" → reversa
- "gerar o banco a partir do modelo" → direta
- "corrigir o modelo e gerar um banco novo" → **reengenharia**
- "manter modelo e banco sincronizados nos dois sentidos" → **round-trip**

> [!warning] Reengenharia tem os três passos
> Reversa é só o 1º passo. Direta é só o 3º. O conjunto (obter → ajustar → regerar)
> é **reengenharia**.

## Técnicas de apoio à reversa

| Técnica | O que faz | Quando |
| --- | --- | --- |
| **Data profiling** | Analisa o **conteúdo** — valores distintos, faixas, nulos, padrões — para inferir domínios e chaves | Banco sem restrições declaradas |
| **Schema compare** | Compara e sincroniza o modelo com o banco | Modelo desatualizado vs. produção |

## Não confundir com

| Termo | Assunto real |
| --- | --- |
| Replicação assíncrona | Alta disponibilidade (cópia entre servidores) |
| Particionamento lógico | Desempenho físico |
| Normalização automática | **Não existe** — ferramenta não normaliza sozinha |
